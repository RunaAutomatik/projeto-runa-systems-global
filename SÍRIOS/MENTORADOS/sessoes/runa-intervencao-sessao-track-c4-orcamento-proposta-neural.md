# Track C4 — ORÇAMENTO$: Proposta e Precificação Neural

> **Fase 5 — Especialização · Track C · Sessão 4 de 4 · Última sessão de especialização**
> **Pré-requisito:** C1 concluída (landing page), C3 recomendada (pipeline de CRM).
> **Resultado desta sessão:** Sistema de proposta neural configurado + 3 propostas reais geradas ao vivo.

---

## Objetivo da Sessão

A maioria das agências perde negócios não na call de vendas — mas na proposta.
Uma proposta mal estruturada gera objeção de preço mesmo quando o serviço é excelente.
Uma proposta sem arquitetura de valor é um orçamento com número — não uma argumentação de compra.

O sistema de proposta neural resolve 3 problemas simultaneamente:
1. **Velocidade:** proposta gerada em minutos, não dias
2. **Consistência:** mesma estrutura, mesmo nível de qualidade, independente do operador
3. **Conversão:** cada seção da proposta responde uma objeção real do cliente

**Ao final desta sessão, o operador terá:**
- ✅ Agente de orçamento configurado e ativo
- ✅ 3 modelos de proposta para seus 3 serviços principais
- ✅ Sistema de precificação com lógica de ancoragem
- ✅ Template de proposta gerado e pronto para envio (PDF ou .docx)

## Block 1 — Por que Propostas Não Convertem

**Duração:** 10 min | **Formato:** Diagnóstico rápido

### O que o cliente realmente está avaliando

Quando um cliente recebe uma proposta, ele está respondendo inconscientemente:

```
1. "Esse fornecedor entende meu problema de verdade?"
   → Problema: a maioria das propostas começa pelo SERVIÇO, não pelo PROBLEMA
   → Consequência: cliente sente que comprou uma solução genérica

2. "Esse preço faz sentido pelo que estou recebendo?"
   → Problema: preço sem âncora parece caro. Mesmo preço com âncora parece razoável.
   → Consequência: negociação de desconto que não precisaria acontecer

3. "O que acontece depois que eu fechar?"
   → Problema: a maioria das propostas não descreve o que acontece na prática
   → Consequência: cliente hesita porque não sabe o que vai experimentar
```

### Os erros mais comuns

| Erro | Frequência | Impacto na conversão |
|------|-----------|---------------------|
| Começa pelo serviço, não pelo problema | 90% das propostas | Alto |
| Preço sem contexto de âncora | 75% | Alto |
| Entregáveis vagos ("suporte", "gestão") | 80% | Médio |
| Sem prova social específica para o ICP | 70% | Médio |
| Sem descrição dos próximos passos | 60% | Alto |
| Proposta igual para ICPs diferentes | 85% | Médio |
| Uma única opção de preço | 65% | Médio |

### O princípio da proposta neural

> A proposta não vende o serviço. Ela vende a **decisão de comprar**.

Uma boa proposta elimina objeções antes que o cliente as verbalize.
Uma proposta neural faz isso usando o vocabulário do próprio cliente — documentado em `wiki/concepts/icp.md`.

## Block 2 — Arquitetura da Proposta Neural: 8 Seções

**Duração:** 20 min | **Formato:** Mapeamento ao vivo

### As 8 seções em sequência obrigatória

```
SEÇÃO 1 — CAPA
  → Nome do cliente, data, nome do projeto
  → Subtítulo: "[RESULTADO ESPERADO] para [NOME DO CLIENTE]"
  (Não: "Proposta Comercial — Serviços de Marketing Digital")

SEÇÃO 2 — O DIAGNÓSTICO
  → Descrição do problema específico do cliente (na voz do cliente)
  → O que acontece se nada mudar
  → O que foi identificado na conversa anterior
  (Esta seção mostra que o operador ouviu e entendeu — não que quer vender)

SEÇÃO 3 — A ABORDAGEM
  → O mecanismo diferente (nome do método — vem do vault/metodo.md)
  → Por que esta abordagem funciona para este problema específico
  → O que a diferencia das alternativas que o cliente já tentou
  (Não revelar tudo — suficiente para criar confiança no mecanismo)

SEÇÃO 4 — O ESCOPO
  → O que está incluído (entregável por entregável, sem jargão)
  → O que NÃO está incluído (elimina mal-entendidos)
  → Responsabilidades do cliente (o que ele precisa fornecer / decidir)
  (Cada entregável deve ser verificável: não "gestão de redes" mas "8 posts/mês + 2 stories/dia")

SEÇÃO 5 — A PROVA
  → 1 case do mesmo ICP com resultado + prazo
  → 1 depoimento específico para o problema desta proposta
  (Usar agente-prova-social: *case-para [perfil do cliente])

SEÇÃO 6 — O INVESTIMENTO
  → 3 opções de preço (ancoragem — ver Block 4)
  → Forma de pagamento + prazo de início
  → O que muda em cada opção (escopo ou duração, nunca qualidade)
  (Nunca uma única opção — 3 opções aumentam a taxa de fechamento)

SEÇÃO 7 — OS PRÓXIMOS PASSOS
  → O que acontece nas 24h após o aceite
  → O que acontece na primeira semana
  → Quando o cliente começa a ver resultado
  (Remove a incerteza do "e agora?" que paralisa a decisão)

SEÇÃO 8 — A VALIDADE
  → Data de validade da proposta (não mais de 7 dias)
  → Disponibilidade atual (vagas — vem do agente-prova-social: *escassez)
  → CTA claro: como aceitar (responder e-mail / assinar digitalmente / mensagem no WhatsApp)
```

### Mapeamento ao vivo: os 3 serviços do operador

O facilitador pede que o operador liste seus 3 serviços principais:

```markdown
## Serviço 1: [NOME]
- Problema central que resolve:
- ICP principal:
- Resultado entregue (com número):
- Prazo de entrega:
- Preço atual:

## Serviço 2: [NOME]
(mesmos campos)

## Serviço 3: [NOME]
(mesmos campos)
```

Esses 3 serviços são os insumos para o agente de orçamento em Block 3.

## Block 3 — Agente de Orçamento

**Duração:** 30 min | **Formato:** Configuração + geração ao vivo

### O agente de orçamento: o que ele faz

O agente lê o vault (ICP, método, casos, FAQ, serviços) e gera a proposta completa para um cliente específico. Não usa template genérico — usa os dados do projeto específico coletados na qualificação.

```yaml
name: agente-orcamento
version: "1.0"

persona: |
  Você é o agente de orçamento de [NOME DO NEGÓCIO].
  Sua função é gerar propostas comerciais específicas para clientes reais.
  Você nunca usa linguagem genérica. Cada proposta começa pelo diagnóstico
  do problema do cliente — documentado na qualificação.
  Você usa o vocabulário do ICP documentado em wiki/concepts/icp.md.
  Você nunca promete o que o método não entrega.
  Toda proposta gerada passa pelo operador para aprovação antes de envio.

vault_dependencies:
  icp: "[VAULT]/wiki/concepts/icp.md"
  metodo: "[VAULT]/wiki/concepts/metodo.md"
  casos: "[VAULT]/wiki/concepts/casos.md"
  servicos: "[VAULT]/wiki/concepts/servicos.md"
  precificacao: "[VAULT]/wiki/concepts/precificacao.md"
  faq: "[VAULT]/wiki/concepts/faq.md"

identidade:
  negocio: "[NOME DO NEGÓCIO]"
  operador: "[NOME DO OPERADOR]"
  validade_proposta: 7 # dias
  moeda: "BRL"

commands:
  proposta:
    trigger: "*proposta [nome do cliente] [serviço] [contexto da qualificação]"
    instrucao: |
      Leia todos os arquivos do vault.
      Gere a proposta completa com as 8 seções em sequência obrigatória.
      Use os dados do cliente passados no contexto da qualificação.
      Use o case mais próximo do perfil do cliente via casos.md.
      Use o sistema de precificação de precificacao.md para montar as 3 opções.
      Máximo 2 páginas A4 de conteúdo (sem capa e sem anexos).
    output_format: |
      # PROPOSTA — [SERVIÇO] PARA [CLIENTE]
      [Data] | Válida até [Data + 7 dias]

      ## Diagnóstico
      [...]

      ## A Abordagem
      [...]

      ## O Escopo
      [...]

      ## A Prova
      [...]

      ## O Investimento
      [...]

      ## Os Próximos Passos
      [...]

      ## Validade e Disponibilidade
      [...]

  ajustar:
    trigger: "*ajustar [seção] [instrução de ajuste]"
    instrucao: |
      Leia a seção especificada da proposta mais recente gerada.
      Aplique o ajuste solicitado mantendo a estrutura e o tom.
      Não reescrever o que não foi pedido para ajustar.
    output_format: |
      ## [SEÇÃO] — revisada

      [Conteúdo ajustado]

      [Motivo do ajuste aplicado em 1 frase]

  opcoes_preco:
    trigger: "*opcoes-preco [serviço] [valor-base]"
    instrucao: |
      Leia wiki/concepts/precificacao.md.
      Gere 3 opções de preço para o serviço especificado.
      Opção 1 (Essencial): valor-base — escopo reduzido
      Opção 2 (Completo): valor-base × 1,4 — escopo completo
      Opção 3 (Premium): valor-base × 2 — escopo completo + suporte prioritário + garantia
      Cada opção deve ter nome, escopo detalhado e o que muda em relação às outras.
    output_format: |
      ## Opções de Investimento — [SERVIÇO]

      | | Essencial | Completo | Premium |
      |---|----------|---------|--------|
      | Preço | R$[X] | R$[Y] | R$[Z] |
      | [Entregável 1] | ✅ | ✅ | ✅ |
      | [Entregável 2] | ❌ | ✅ | ✅ |
      | [Entregável 3] | ❌ | ❌ | ✅ |
      | Suporte | E-mail | E-mail + WhatsApp | WhatsApp + reunião semanal |
      | Garantia | — | — | [GARANTIA] |

      **Recomendação:** Opção [X] para o perfil deste cliente.
      **Por quê:** [1 frase]

  exportar:
    trigger: "*exportar [formato: pdf|docx|markdown]"
    instrucao: |
      Formate a proposta mais recente aprovada para o formato especificado.
      PDF: escrever o markdown formatado para copiar em ferramenta de PDF.
      DOCX: usar estrutura compatível com python-docx (H1/H2/H3 nativos).
      Markdown: limpar e formatar para envio direto via Notion ou email.
    output_format: |
      [Proposta formatada no formato solicitado]

      [Instruções de exportação para o operador]

scope:
  can:
    - Gerar proposta completa com as 8 seções
    - Ajustar seções específicas sem reescrever tudo
    - Gerar 3 opções de preço com lógica de ancoragem
    - Exportar em múltiplos formatos
    - Manter consistência com o método e o ICP documentados no vault
  cannot:
    - Inventar resultados ou casos não documentados
    - Prometer resultado que o método não entrega
    - Enviar proposta sem aprovação do operador
    - Criar preços fora da tabela de precificacao.md sem instrução explícita
```

### Geração ao vivo: 3 propostas em 30 minutos

```
Proposta 1 — Serviço principal para cliente ideal do ICP (10 min)
  *proposta "João Silva / Construtora ABC" "gestão de conteúdo" "problema: sem presença digital, 3 tentativas com freelancers, orçamento até R$3k/mês"

Proposta 2 — Serviço secundário para ICP variante (10 min)
  *proposta "[NOME]" "[SERVIÇO 2]" "[CONTEXTO]"

Proposta 3 — Proposta de menor ticket (entrada) (10 min)
  *proposta "[NOME]" "[SERVIÇO 3]" "[CONTEXTO]"
```

Para cada proposta:
1. Agente gera o texto completo
2. Operador revisa e aprova (ou pede ajuste via `*ajustar`)
3. Agente exporta em markdown para copiar no documento de envio

## Block 4 — Sistema de Precificação com Ancoragem

**Duração:** 20 min | **Formato:** Estruturação ao vivo

### O princípio da ancoragem

O preço nunca é avaliado em absoluto — sempre é avaliado em relação a algo.

```
R$3.000/mês sem âncora → parece caro
R$3.000/mês depois de ver a opção de R$5.500/mês → parece razoável
R$3.000/mês depois de calcular o custo do problema → parece investimento
```

A ancoragem funciona em 3 dimensões:
1. **Âncora de preço:** mostrar a opção mais cara primeiro
2. **Âncora de custo:** calcular o custo do problema não resolvido
3. **Âncora de comparação:** comparar com o custo de fazer internamente

### O arquivo `wiki/concepts/precificacao.md`

Criar durante a sessão com o operador:

```markdown
## Precificação — [NOME DO NEGÓCIO]

### Princípios de precificação

1. Sempre 3 opções — nunca 1
2. Opção central é a que queremos que o cliente escolha (maior margem)
3. Opção premium âncora a opção central
4. Opção básica serve como qualificação (cliente que escolhe básico → outro perfil de ICP)

### Tabela de serviços e preços

| Serviço | Essencial | Completo (alvo) | Premium | Custo de produção |
|---------|----------|-----------------|---------|------------------|
| [Serviço 1] | R$[X] | R$[Y] | R$[Z] | R$[custo] |
| [Serviço 2] | R$[X] | R$[Y] | R$[Z] | R$[custo] |
| [Serviço 3] | R$[X] | R$[Y] | R$[Z] | R$[custo] |

### Cálculo de âncora de custo

Para o ICP principal:
- Custo do problema por mês: R$[X] (em tempo perdido / oportunidade não convertida)
- ROI mínimo esperado do serviço: R$[Y]
- Múltiplo: [Y] ÷ [preço completo] = [X]x de retorno

### Argumentação de preço

Quando cliente questionar:
"O investimento mensal é R$[PREÇO]. Para colocar em perspectiva:
[PROBLEMA não resolvido] custa aproximadamente R$[CUSTO DO PROBLEMA]/mês.
O resultado esperado em [PRAZO] é [RESULTADO COM NÚMERO].
O retorno projetado é de [MÚLTIPLO]x sobre o investimento."

### Condições de pagamento

- Padrão: 50% no contrato + 50% na entrega / 30 dias após início
- Pagamento à vista: -10%
- Contrato de 6 meses: -15% no total
- Contrato de 12 meses: -20% no total + prioridade de agenda
```

### Exercício de ancoragem ao vivo

O facilitador faz o operador calcular ao vivo para o serviço principal:

```
1. Qual é o custo do problema para o cliente típico?
   (Ex: "um projeto de site mal feito custa R$8k e não converte nada")

2. Qual é o resultado que você entrega em números?
   (Ex: "landing page que converte 3–5% dos visitantes em leads")

3. Qual é o múltiplo de retorno?
   (Ex: "R$3k de investimento vs R$8k economizado = 2,7x só no primeiro ciclo")

4. Como isso aparece na seção de investimento da proposta?
   "O investimento de R$3.000 representa [X]x de retorno estimado
    nos primeiros [PRAZO], baseado no caso de [CASE]."
```

## Block 5 — Entrega e Follow-up + Desafio C4

**Duração:** 10 min | **Formato:** Protocolo + checklist

### Protocolo de entrega da proposta

```
PASSO 1 — Antes de enviar:
  → Aprovação do operador em todas as 8 seções
  → Verificar: nome do cliente correto, preço correto, data de validade correta
  → Exportar: *exportar markdown (ou docx)

PASSO 2 — Canal de envio:
  → E-mail + WhatsApp (sempre os dois — e-mail para registro, WhatsApp para urgência)
  → E-mail: anexar PDF ou link Google Docs + texto de apresentação de 3 linhas
  → WhatsApp: "Acaba de chegar no seu e-mail a proposta que conversamos. Já deu uma olhada?"

PASSO 3 — Follow-up automático (n8n C2/C3):
  → n8n já está configurado com a sequência de 5 toques
  → Operador apenas move o prospect para estágio "PROPOSTA ENVIADA" no CRM
  → n8n cuida do follow-up nos dias 2, 5, 8, 12, 15
```

### Texto de apresentação da proposta (e-mail)

```
Assunto: [NOME DO CLIENTE] — Proposta [SERVIÇO] · Válida até [DATA]

[NOME],

Conforme conversamos, segue a proposta para [SERVIÇO].

Ela está estruturada em 3 opções — de acordo com o escopo e o investimento
que faz mais sentido no momento para o [NEGÓCIO DO CLIENTE].

Fico disponível para alinhar qualquer ponto antes da sua decisão.

[NOME DO OPERADOR]
[CONTATO]

P.S. A proposta é válida até [DATA]. Se quiser garantir o início em [MÊS], me avise.
```

## Notas para o Facilitador

### Quando o operador não tem preços definidos

Se o operador ainda não sabe quanto cobrar:
1. Fazer o exercício de custo do problema (Block 4) PRIMEIRO
2. Usar o resultado para definir o preço mínimo (resultado esperado ÷ múltiplo 3x)
3. Não deixar a sessão terminar sem 3 valores definidos — mesmo que sejam provisórios

Propostas com preços "a definir" nunca são enviadas.

### Quando o operador tem medo de cobrar mais

Sintoma: coloca preços 30–50% abaixo do que calculou no exercício.

Intervenção do facilitador:
1. "Você calculou que o problema custa R$[X] e que você entrega R$[Y] de resultado."
2. "Por que você está cobrando R$[Z] — que é menos de 50% do valor que você gera?"
3. Geralmente o bloqueio é posicionamento, não o serviço. Recomendar B3 se ainda não fez.

### Quando o operador não tem cases para a seção de prova

Se o banco de provas está vazio:
1. Usar o próprio resultado do programa como case (se aplicável)
2. Referenciar um resultado de projeto anterior sem formalização
3. Ser honesto: "Ainda estou construindo meu banco de cases. O que já posso mostrar é [X]."
4. Planejar construir os primeiros 3 cases nas próximas 4 semanas (B4)

### C4 é o fechamento do Track C — também é uma virada

Após C4, o operador tem:
- Landing page no ar (C1)

Isso é o squad operacional completo de uma agência neural.
O facilitador encerra com: "Você construiu o sistema. As próximas sessões (S18–S20) orquestram tudo."
